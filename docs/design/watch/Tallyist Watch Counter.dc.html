Design reference · DrinkTrackerWatch · Phase 3–6

The watch counter, and the tap that hides the number

Today's counter narrowed to 198 × 242 pt, with the day's DayIntensity painted behind the numeral and one tap to put the digits away while the band stays lit. Dark ground only. Every value below is transcribed from shipping Swift or derived from it by a stated ratio; nothing here is eyeballed.

Read this first

This page is a design reference drawn in HTML, not code to port. The target is a SwiftUI watchOS view in DrinkTrackerWatch/, built from the repo's own components and tokens. Where a value here names a Swift symbol, call the symbol rather than copying the number — the hex codes are printed so the drawing can be checked, not so they can be pasted. IntensityPalette remains the only place in the app that defines literal colours (PRD invariant 10).

Fidelity: high. Layout, type sizes, radii and colours are final and measured. Recreate them exactly. The one element that is not settled is marked in place: the “Record no alcohol” button on the empty‑day screen is a proposal with no decision behind it.

Constraints this design is built to respect
No goals, no streaks, no scores. Nothing on this screen accumulates toward anything, and no shape implies a target — which is why the band is a tile rather than a bar or an arc that fills. Colour never grades. The ramp carries magnitude in lightness only, alcohol‑free sits off it with an outline, status is shape and words first. One tap is the fast path (invariant 1), and it cannot mean different things here and in the widget — so ＋ runs the same seed rule, read from the App Group. Region is a display lens (invariant 3): every figure is expressed in the region the settings bridge delivered, never a US default. Voice: factual, countable, states of the system and not the person, and no exclamation marks — the storage warning included.

Two ratios, so the tile can be resized honestly
The phone's hero is a 68 pt numeral in a 126 pt tile at radius 36. Both watch values are that, scaled: radius = side × 36 / 126 → 25, and numeral = side × 68 / 126 → 46. If the tile ever changes size — another case, an accessibility step — re‑derive from these rather than picking new numbers.

The 2.59:1 in row one is why the session dots start at .medium — a dot is a graphical object needing 3:1 against its ground, and .low does not clear it. A .low dot stays on the neutral outline, which is the design system's existing off‑ramp channel. The tile is exempt, and deliberately: it is 86 pt of fill carrying a numeral at 6.94:1, not a 9‑pt mark whose colour is the whole message. Recompute all four before changing any of them; a colour error here is invisible to a reviewer with normal colour vision.
Behaviour the code owns
＋ writes through DrinkDraft.quickCount(1, from:seed:region:) with region and seed read from AppSettings.storedRegion() / storedCounterSeed(). Lift the shared body into Shared/ and call it from both here and LogOneDrinkIntent — a fourth copy of the seed rule will drift, which is the whole of ADR‑0023's argument. − goes through DrinkRepository.delete(id:) on the entry returned by a new pure removableNewest(in:on:calendar:); nil means the control is unavailable, never skipping to an older drink. Both refetch at execution time and chain like TodayView's counterOps, so a fast − behind a ＋ removes the drink that ＋ just made rather than the one before it. Double Tap is .handGestureShortcut(.primaryAction) on ＋ and nothing else claims it. Haptics: .click on a log, .failure on a refusal, a distinct one for a Double Tap log so an unintended pinch announces itself — and never .success, which reads as praise.
The hide state
A @State boolean on the counter view, toggled by a tap on the tile — 86 pt, so no new affordance is needed. Per‑glance, not stored: it clears on launch, writes nothing to defaults, and never gates a write. When true, suppress the numeral (bar in its place), the ≈ line, the four legend labels, and the session dots' fill — they fall to outlines. Keep the tile fill, the swatches, the unit word and both controls. This is orthogonal to .privacySensitive(), which still applies to every figure and composes on top.
Motion, and the one thing that jumps
The numeral rolls on a value change: .contentTransition(.numericText(value:)) + .snappy(duration: 0.2). The tile's fill and ink crossfade on their own clock at .smooth(duration: 0.22), gated by Reduce Motion, exactly as CountStepper does. Hiding is a subject change, not a value change, so numeral → bar must crossfade and must not roll — a roll would draw a direction the app does not assert. Watch out: the legend re‑lays‑out when the labels leave, which moves the swatches. Either crossfade the whole row or pin its width so it cannot shift; do not animate the gap.

The tile shrinks to a disc and keeps its job. Session count while a session runs, today's count otherwise — the same rule the home‑screen widget follows, no more. StaticConfiguration throughout. Build the timeline with two entries — the current one, and one dated session.lastDrinkAt + SessionPace.gapThreshold with the post‑session state, refresh policy .after that date — or a dead session's count sits on the face until something else triggers a reload, which is the standing number the tone rules forbid. accessoryInline cannot show a block at all, so it is the one family where hiding means the figure simply goes. Use LogOneDrinkIntent and never LogDrinkIntent: a promptable parameter is the bug that once broke one‑tap logging, and a parameterless intent structurally cannot repeat it. No relevance‑based Smart Stack surfacing — “you usually drink around now” is a behavioural prediction dressed as help.

Whole‑phrase keys carrying their own count, never a number glued to a noun — the unit's name varies by region, its form by count, and word order by language. Two of these are not drawn on this page: the −‑unavailable line and the region‑not‑set line both replace the ≈ line in their states.
Accessibility — non‑negotiable
The counter is one adjustable element, not three stops: accessibilityElement(children: .ignore), label “Drinks today”, value the count, and an accessibilityAdjustableAction for increment and decrement. The tile stays out of the tree entirely — the value already says the number, and the colour encodes nothing a reader needs twice.
Hiding must not change what VoiceOver speaks. A screen reader is not the audience the tap protects, and silencing the value would make the feature an accessibility regression dressed as privacy. Same for the legend: each band is one element with its range as the label and .isSelected on the active one, labels visible or not.
Both discs are 44 pt with the hit shape inside the button's label — a frame applied to the Button grows the layout without growing the target. Every text style relative, minHeight never height. Colour carries nothing alone: the ramp is lightness‑ordered so it survives every CVD and greyscale, alcohol‑free adds an outline, and the storage warning is a symbol plus words.
Open before this is built — five things, none of them cosmetic
1Recording a day as no alcohol has no watch path. The phone offers it on an empty day; the plan gives the watch no equivalent, and the wrist is the surface you are wearing at the end of a dry day. The button drawn on the empty‑day screen is a proposal. Decide before Phase 3, because it changes that screen's layout. 2The ＋ in accessoryCircular. Phase 6 puts an interactive ＋ in both the circular and rectangular families, but a 50‑pt disc cannot hold a figure and a 44‑pt target. This design keeps the figure there and leaves the ＋ to accessoryRectangular. Either confirm that, or make the whole circle the button and give up the count. 3Per‑glance or stored? Drawn as per‑glance: nothing persisted, cleared on launch. A stored preference is discreet before the wrist is on the table, which is the only kind that helps — but it needs a switch, and the watch has no real Settings screen. If stored, it is watch‑local by the plan's own rule: it changes what is shown, not what is computed. 4Does hiding govern the complications? It has to, if it is stored. A face needs no unlock and is the most public surface the product has, so a setting that governed only the app would protect the one screen nobody else was looking at. 5What .privacySensitive() actually renders in Always‑On and at each complication size is a device question. The redaction policy here is sound; the redacted tile may not look the way this page draws it. Check it in Phase 6, not Phase 8 — the answer may send the design back.
