# The Tallyist Design System

**Status:** v1.0, reviewed · **Owner:** design · **Code home:** `DrinkTracker/DesignSystem/`
**Synced to:** claude.ai/design, project *Tallyist Design System*

Tallyist's visual language is **native iOS with one voice added**. The system does
not replace Apple's material system — it rides it: system semantic colours, system
type, Liquid Glass surfaces, SF Symbols. The brand layer is deliberately thin and
deliberately consistent: one hue, one numeral style, one way of speaking. An app
about noticing exactly one thing should look like it notices exactly one thing.

Everything here is either shipping in code today (cited by file) or explicitly
marked *proposed*. A design system that describes an imaginary app is a mood board.

---

## 1. Brand foundations

### The idea

A tally is the humblest form of record-keeping: a mark per event, no judgment,
legible at a glance. That is the product's ethic (PRD §1 — report, don't grade)
made visual. Every brand decision derives from it:

| Principle | Consequence |
|---|---|
| **A mark, not a message** | The identity is the tally glyph. No mascot, no illustration style, no decorative shapes. |
| **Count is the hero** | The biggest thing on any surface is a number the user made. Brand recedes behind data. |
| **One hue** | Blue does every branded job — accent, data, icon. A second hue would eventually become a verdict (ADR-0007). |
| **Calm by construction** | Nothing pulses, badges, or celebrates. Motion confirms; it never rewards. |

### The mark

Four vertical strokes and a slash — the canonical tally of five. On the icon:
near-white strokes with the slash in ramp 250, tilted −4° (the same two-tone
hierarchy and tilt as the onboarding hero), on a vertical field of ramp 600→700
centred on the documented 650. Generated by `scripts/make-app-icon.py`; the
geometry there is the reference. Use the mark alone; never lock it up with text,
never recolour it, never show a partial tally (a tally of three reads as a
count, and the icon must not appear to count anything).

### Voice

The verbal identity is already settled law — ADR-0001 (no celebration), ADR-0006
(no scores), the 1.4.3 copy review. As design tokens:

- **Factual and countable.** "3 drinks today", "Record no alcohol today".
- **States of the system, not the person.** "Not syncing", never "you haven't…".
- **No exclamation marks anywhere in the product.** One is permitted in the
  entire system: the storage-failure warning, where alarm is the accurate tone.

## 2. Colour

### The Tallyist Blue ramp

One hue family, twelve steps, shared with the data layer (`IntensityPalette`).
Validated — monotone lightness, CVD-safe as used; see ADR-0007. **Changes are
re-validated, never eyeballed** (PRD invariant 10).

| Step | Hex | Step | Hex | Step | Hex | Step | Hex |
|---|---|---|---|---|---|---|---|
| 100 | `#cde2fb` | 250 | `#86b6ef` | 400 | `#3987e5` | 550 | `#1c5cab` |
| 150 | `#b7d3f6` | 300 | `#6da7ec` | 450 | `#2a78d6` | 600 | `#184f95` |
| 200 | `#9ec5f4` | 350 | `#5598e7` | 500 | `#256abf` | 650 | `#104281` |
| | | | | | | 700 | `#0d366b` |

### Roles

| Token | Light | Dark | Measured contrast |
|---|---|---|---|
| `accent` (interactive text, glyphs, fills) | **500** `#256abf` | **400** `#3987e5` | text: 5.26:1 light / 4.79:1 dark — AA normal, both modes |
| `accent.onFill` (label on accent fill) | white | white | 5.39:1 on 500 — AA normal. On dark, fills stay **500** (see review R2) |
| `brand.deep` (icon field) | 650 `#104281` | 650 | 9.66:1 vs white mark |
| `data.low / .medium / .high` | 250 / 450 / 700 | 600 / 400 / 200 | per ADR-0007, validated both modes |

**Where brand colour may appear — exhaustively:** interactive elements (buttons,
links, selected states), the data ramp, the app icon, the widget's ＋. Everywhere
else is system semantic colour (`primary`, `secondary`, `.fill` tiers), so
surfaces, text, and materials keep Apple's automatic light/dark/vibrancy
behaviour. `GlassTokens` still defines **no colours**; the brand layer lives in
the asset catalog (`AccentColor`) and `IntensityPalette` only. See ADR-0010.

**What brand colour may never do:** grade a day, reward a number, or mark a
"good" state. Status uses shape + words (checkmark symbol, factual copy), with
colour as reinforcement only.

### Neutrals

All system: `Color.primary/.secondary/.tertiary`, `.fill` hierarchy, and the
Liquid Glass material via `glassSurface()`. The system defines no custom greys —
that is a feature, and it is why the app already renders correctly in both
appearances and under Reduce Transparency.

## 3. Typography

System fonts only. The signature is a single rule:

> **Numerals the user made are rounded. Everything else is default SF.**

Rounded (SF Rounded) marks *the user's own data* — the counter, the widget count,
stat values. Chrome, labels, and body stay default-design SF. This gives Tallyist
recognisability with zero font licensing, zero bundle weight, and full Dynamic
Type behaviour.

| Role | Spec | Code |
|---|---|---|
| Hero count | 76 semibold rounded (68 in the stepper) | `GlassTokens.Typography.metric`, `CountStepper` |
| Card value | title, semibold, rounded | `.cardValue` |
| Sheet title | title2 semibold | `.sheetTitle` |
| Onboarding headline | largeTitle bold | `.onboardingHeadline` |
| Section label | footnote medium, uppercase | `SectionLabel` |
| Card label / captions | footnote / caption, secondary | `.cardLabel`, `.supporting` |

All roles are relative text styles (Dynamic Type scales them); fixed sizes appear
only in the two hero numerals and the widget, where layout is width-driven.
Controls wrap text with `minHeight`, never fixed `height` (the Dynamic Type audit
made this a rule; fixed heights clip).

## 4. Space, shape, depth

| Token | Value | Use |
|---|---|---|
| `tight / regular / section / block` | 8 / 12 / 24 / 32 | intra-group → between blocks |
| `screenMargin` | 20 | every screen edge |
| `cardPadding` | 16 | inside cards and rows |
| `Radius.control / pill / card / sheet` | 14 / 22 / 26 / 34 | continuous corners, nested small→large |
| `minimumTouchTarget` | 44 | every interactive element |

Depth comes from the system material (`glassSurface()` → `.glassEffect`), never
from custom shadows. ComponentsKit shadows are pulled back in `AppTheme` for the
same reason. One elevation story, owned by the OS.

## 5. Motion

Motion has exactly two jobs here: confirm a change, and keep numbers legible
while they change.

| Pattern | Spec | Where |
|---|---|---|
| Value change | `.snappy` + `.contentTransition(.numericText)` | counter, totals, estimates |
| Structure change | `.smooth(duration: 0.25)` + opacity/move | disclosures, undo bar, repeat row |
| Confirmation | `.sensoryFeedback(.selection)` | stepper taps, including bound-hits |

Never: springs with overshoot on numbers, looping or idle animation, motion that
draws the eye to a "good" value. If an animation would make a rising number feel
like a score increasing, it is wrong (ADR-0006 applied to motion).

| **Selection action bar** | `Calendar/CalendarView.swift` (`selectionBar`) | Bottom-pinned glass bar (radius 22): live day count, one-tap "Mark no drinks" (AccentFill under white), "Log drinks…" to the bulk sheet, 32pt dismiss. From the prototype handoff, carrying ADR-0011 semantics |
| **Bulk fill sheet** | `Calendar/BulkFillSheet.swift` | The day sheet's counter applied to a dragged run of days; skips recorded days and says so (ADR-0011) |

Composition rules: one primary action per surface; controls on glass, never glass
on glass; a screen leads with the user's number, never with chrome.

## 7. Accessibility (non-negotiable layer)

- 44pt targets everywhere; the hero stepper uses 64pt.
- Dynamic Type: relative styles + `minHeight` wrapping; `FlowLayout` where pills
  can wrap; year grid is read as twelve month summaries, not 365 stops.
- Colour never carries meaning alone: the ramp is lightness-ordered (survives all
  CVD + greyscale), alcohol-free adds an outline, status adds symbol + words.
- VoiceOver: counters are adjustable elements; cells speak date + amount in
  words; every icon-only button has a label.
- Contrast: every accent role ≥ 4.5:1 in both modes (table in §2 — measured, not
  assumed).

## 8. Design review (director pass) — findings and resolutions

Reviewed against: HIG, WCAG 2.1 AA, PRD §1/§2, ADR-0001/0006/0007. Method:
contrast computed, every claim checked against code, tone rules applied to
visuals as well as copy.

**R1 — Accent failed AA as text. Fixed.** The draft used ramp 450 `#2a78d6`
(the data-ramp midpoint) as the accent. Measured: 4.30:1 as text on the light
surface and 4.42:1 for white on its fill — both under the 4.5:1 normal-text bar.
Resolution: **accent is 500 in light, 400 in dark** (5.26 / 5.39 / 4.79:1).
Data keeps 450 — data marks are not text, and the ramp is validated separately.
Lesson recorded: *the data ramp and the interactive accent are different jobs;
sharing one step between them was the error.*

**R2 — Dark-mode fills can't take the dark-mode accent.** White on 400 is
3.64:1. Resolution: fills use **500 in both modes** (white label 5.39:1
everywhere); only accent *text and glyphs* switch to 400 in dark. The single
`AccentColor` asset carries the text-accent pair (500/400); ComponentsKit's
primary button is themed to the fill token in `AppTheme`, and native fills use
the dedicated `AccentFill` asset (500, both modes) — after an audit found one
site (`SizePill`) filling with the text accent. *Remaining follow-up:* eyeball
the dark-mode fills on device.

**R3 — The icon mark and the ramp told different blues.** The draft icon used
650 while the accent moved to 500, risking a family of near-miss blues.
Resolution: icon field stays 650 (it needs the 9.66:1 mark contrast); §2 now
names every permitted blue and its job, so "another blue" has nowhere to hide.

**R4 — Missing states.** The draft specified components only at rest. Added:
pressed = system-provided (glass interactive highlight / `SUButton`'s own),
disabled = 40% opacity + `.disabled` (as `CountStepper` already does), selected
= accent fill with white content (as `SizePill`). No custom hover/focus
inventions — the OS owns them.

**R5 — Tone risk in motion.** The draft allowed `.snappy` everywhere; on a
rising count that can read as celebration. Resolved by the motion rule in §5:
numeric transitions confirm, never emphasise — same physics whether the number
rises or falls.

**Verdict:** approved as v1.0 with R1–R5 applied. Open follow-ups: R2 device
check; export the ramp as Figma variables if a Figma library is ever started.

### Prototype handoff (2026-08) — what was adopted, and what was reconciled

The claude.ai/design prototype *Tallyist iOS Prototype* delivered three changes
(handoff record: the `design/tallyist-prototype` branch). Disposition:

- **Calendar enlargement — adopted as specified.** The month grid and weekday
  header bleed 10pt past the screen margin per side; cell side rises to ~49pt on
  a 402pt device. The height reserve is now computed from measured width — the
  old hardcoded 52pt bound would have clipped the widest iPhones post-bleed.
- **Onboarding refresh — adopted, copy verbatim.** Tally hero, lock hero,
  progress dots, all decorative motion behind Reduce Motion. One colour
  substitution: the handoff's slash tint `#7FA9DD` is the accent at ~55% over
  the light surface, so it ships as `accentColor.opacity(0.55)` — same pixels in
  light mode, dark mode derived for free, and no new blue enters ADR-0010's
  registry.
- **Drag-to-prefill — UI adopted, semantics kept.** The prototype's action bar
  and selection visuals (ring everywhere, wash only on writable days) replace
  the release-straight-into-sheet flow, at the user's direction. What the bar
  *does* is unchanged from ADR-0011: recorded days are never touched, and the
  counted path ("Log drinks…") keeps the capability the prototype's no-drink-only
  bar would have dropped. Two engineering divergences, both deliberate: the
  gesture keeps its 0.25s hold (a bare drag fights the scroll view), and the bar
  gains a second row for the two actions. The bar's "Mark no drinks" privileges
  the most common bulk answer; zero-as-a-value survives in both sheets.

## 9. Governance

- Changes to colour tokens: re-run the contrast math and (for ramp steps) the
  ordinal validation. Numbers go in the table; "looks fine" doesn't.
- Changes to voice-adjacent visuals (anything that could read as a verdict):
  check against ADR-0001/0006/0007 and the copy review.
- The sync'd claude.ai/design project mirrors this document; update both in the
  same change or note the drift here.
